# Сервисный Telegram-бот: ИИ понимает вопрос, ответ берётся из базы знаний

Небольшой прототип на Python 3.11+ для сервисного отдела. Вопрос клиента понимает
**маленькая ИИ-модель**, но текст ответа она не пишет: модель может только **выбрать
подходящую запись базы знаний** или сказать «в базе этого нет». Клиенту всегда уходит
`answer` этой записи **дословно**, а если записи нет — фиксированный отказ и
направление в сервисный отдел.

Так работает и Telegram-бот, и веб-демо: оба используют один и тот же
`AIAssistant` + `AnswerEngine`, поэтому поведение одинаковое.

## Что реализовано

| Вопрос клиента | Ответ |
| --- | --- |
| Как почистить / обслужить КАН Ультра? | Видео: https://youtu.be/WW1Hqh3_WNk |
| Как часто обслуживать КИТ? | Рекомендуем проводить обслуживание один раз в год. |
| Переполнена станция, что делать? | Точный предоставленный ответ о проверке электрического блока, обесточивании при затоплении и обращении в сервис. |
| Как почистить станцию Тверь? | Нет информации в базе; обращение в сервисный отдел. |

Формулировки распознаются по смыслу: «как почистить КАН Ультра», «есть инструкция по
обслуживанию КАН?», «как часто надо чистить КИТ», «вода переливается через край»,
«что делать, если станция переполнена» — всё это находит нужную запись.

Бот не переносит периодичность КИТ на КАН и не выдаёт видео КАН за инструкцию для
другой станции. Телефон и адрес сервисного отдела не предоставлены и не выдумываются.

## Как устроено решение

```text
вопрос клиента (любыми словами, без кнопок)
        │
        ├─ жёсткие правила базы ── неизвестная модель («Тверь», «КАН Лайт»),
        │                          тема вне базы (цена, ремонт, гарантия, фильтр),
        │                          несколько моделей/тем, отрицание
        │                          → отказ, ИИ даже не спрашивают
        │
        ├─ ИИ-модель (если настроена) ── получает только базу знаний и возвращает JSON:
        │        {"action":"answer","entry_id":"..."}  — выбрать запись
        │        {"action":"clarify"}                  — попросить модель станции
        │        {"action":"no_answer"}                — в базе нет ответа
        │
        └─ детерминированные правила ── резерв: если ИИ выключен, недоступен, ответил
                                       ошибкой или выбрал недопустимую запись
        │
        ▼
текст ответа = запись базы знаний дословно  →  Telegram / веб-демо
```

- `service_bot/llm.py` — провайдер-агностичный клиент (OpenAI-совместимый), цепочка
  провайдеров, таймауты, повторы с учётом `Retry-After`, предохранитель на 3 ошибки;
  ключ никогда не логируется и не попадает в статусы.
- `service_bot/ai.py` — промпт, «дигест» базы знаний, проверки выбора модели и
  прозрачное поведение при недоступности модели.
- `service_bot/engine.py` — детерминированная политика и **единственный** конструктор
  фактического ответа `answer_reply()`, который копирует `entry.answer`.
- `service_bot/knowledge.py` — строгая валидация базы (структура, ссылки, пары
  модель/тема, синонимы, регулярные выражения).

### Какая именно ИИ используется

Модель подключается переменными окружения, код один и тот же:

| Провайдер | Как включить | Что используется по умолчанию |
| --- | --- | --- |
| Бесплатный внешний шлюз llm7.io | ничего: `LLM_PROVIDER` по умолчанию `llm7` | `GLM-5.3-Flash`, ключ не нужен |
| GitHub Models (бесплатно с токеном Actions) | `LLM_PROVIDER=github` + `GH_MODELS_TOKEN` (в Actions это `${{ github.token }}` с `permissions: models: read`) | `openai/gpt-4o-mini` |
| OpenAI-совместимый API | `LLM_API_KEY` (+ `LLM_BASE_URL`, `LLM_MODEL`), режим `auto` выберет его первым | `https://api.openai.com/v1`, `gpt-6-luna` |
| OpenRouter / Groq / DeepSeek / Mistral / Gemini | `LLM_PROVIDER=openrouter|groq|deepseek|mistral|gemini` + ключ | маленькая модель провайдера (`openai/gpt-oss-20b`, `gemini-3.5-flash-lite`, …) |
| Локальная модель (Ollama, LM Studio) | `LLM_PROVIDER=ollama` | `http://127.0.0.1:11434/v1`, `llama3.2` |
| Резервный keyless-вариант | `LLM_PROVIDER=pollinations` | `openai` (в CI отвечал 402, оставлен запасным) |
| Без ИИ вообще | `AI_ENABLED=0` | отвечают только правила базы |

Режим `auto` (по умолчанию) собирает **цепочку**: ключ → GitHub Models (если есть токен
workflow) → бесплатные внешние шлюзы. Первый провайдер, который ответил, выигрывает,
остальные остаются прозрачным резервом.

В этом репозитории ИИ-слой проверен на живом ключе владельца (Google AI Studio,
`gemini/gemini-3.5-flash-lite`): модель вернула решения по смыслу на четырёх
контрольных вопросах из пяти за 0,5–0,6 с, пятый («станция Тверь») блокируется
правилами до обращения к модели. Ответы при этом по-прежнему копируются из базы
дословно. Если модель недоступна или лимит исчерпан, отвечают правила базы.

Модель легко заменить на корпоративный шлюз: `LLM_PROVIDER=custom`, `LLM_BASE_URL`,
`LLM_MODEL` и секрет `LLM_API_KEY`. Внешние бесплатные шлюзы не дают SLA и видят текст
вопроса клиента — для эксплуатации лучше свой ключ или локальная модель.

### Как подключить свой ключ за 5 минут

1. Возьмите бесплатный ключ у одного из провайдеров (банковская карта не нужна):
   - **Google AI Studio** — https://aistudio.google.com/apikey, модель по умолчанию
     `gemini-3.5-flash-lite` (есть бесплатный тариф);
   - **Groq** — https://console.groq.com/keys, модель `openai/gpt-oss-20b`;
   - **OpenRouter** — https://openrouter.ai/keys, любую бесплатную модель;
   - **OpenAI** — https://platform.openai.com/api-keys, модель `gpt-6-luna`
     (самая дешёвая, но это платный тариф).
2. Откройте *Settings → Secrets and variables → Actions → Secrets → New repository
   secret*: имя `LLM_API_KEY`, значение — ваш ключ. Ключ не попадает ни в код, ни в
   логи, ни в сообщения бота.
3. Если провайдер не OpenAI, на вкладке *Variables* создайте переменную
   `LLM_PROVIDER` со значением `gemini`, `groq`, `openrouter`, `deepseek` или
   `mistral`. Для OpenAI достаточно одного секрета — режим `auto` выберет его первым.
   Дополнительно режим `auto` понимает ключ по префиксу (`AIza…` — Google, `gsk_…` —
   Groq, `sk-or-…` — OpenRouter) и по отдельным переменным (`GEMINI_API_KEY`,
   `GROQ_API_KEY`), но явная переменная `LLM_PROVIDER` надёжнее.
4. Перезапустите бота: *Actions → Telegram - hosted bot (scheduled AI sessions) →
   Run workflow*. В шаге «Check the AI layer» должно появиться `layer=llm` и имя
   модели; команда `/status` в боте показывает подключённую цепочку.
5. Найдите точное имя модели в личном кабинете провайдера и при необходимости
   задайте его переменной `LLM_MODEL` — список моделей у провайдеров меняется.
   Если указанное имя уже не существует, бот сам попробует запасные имена из пресета
   (для Gemini — `gemini-3.1-flash-lite`, `gemini-2.5-flash`) и покажет в `/status`,
   какая модель реально отвечает. Опечатка в `LLM_MODEL` не выключает провайдера:
   ответ просто формируют правила базы.

Корпоративный шлюз (в том числе YandexGPT, GigaChat и другие OpenAI-совместимые
сервисы) подключается так же: `LLM_PROVIDER=custom`, `LLM_BASE_URL=<адрес>/v1`,
`LLM_MODEL=<модель>` и секрет `LLM_API_KEY`.

Проверить подключение можно командами:

```bash
python -m service_bot ai-check            # провайдеры, решения по тестовым вопросам, состояние цепочки
python -m service_bot ai-check --offline  # настройка и промпт без сети
```

## Где база знаний и как её менять

**`knowledge/knowledge_base.json` — единственный источник фактических ответов.**
ИИ-модель не имеет других источников: она видит только этот файл (см. `knowledge_digest()`).

- `stations`: идентификаторы моделей, названия и допустимые варианты написания.
  «КАН» — явно заданный синоним «КАН Ультра» в этом прототипе, не правило для всех КАН.
- `intents`: темы и словари формулировок: обслуживание, периодичность, переполнение.
- `entries`: модель + тема + **утверждённый текст ответа** + источник + примеры вопросов.
- `context_word_patterns`: допустимые служебные слова и формы русского языка.
- `unsupported_topic_patterns`: темы, которых нет в текущей базе (ремонт, химия, цены,
  монтаж). Вопросы с этими словами блокируются до обращения к ИИ.

### Пример добавления сведений о новой модели

Сначала сервисный отдел должен предоставить точный текст. **Не добавляйте сведения
из предположений или общих знаний ИИ.** Существующая база специально не содержит
инструкции для Твери.

1. Добавьте в `stations` модель (название должно входить в `aliases`):

   ```json
   {
     "id": "new_station",
     "name": "НОВАЯ МОДЕЛЬ",
     "aliases": ["НОВАЯ МОДЕЛЬ"]
   }
   ```

2. Добавьте в `entries` запись с настоящим утверждённым текстом и источником:

   ```json
   {
     "id": "new_station_maintenance",
     "station_id": "new_station",
     "intent_id": "maintenance",
     "title": "Обслуживание НОВОЙ МОДЕЛИ",
     "answer": "<ТОЧНЫЙ ТЕКСТ, УТВЕРЖДЁННЫЙ СЕРВИСНЫМ ОТДЕЛОМ>",
     "source": {"label": "<НАЗВАНИЕ ИНСТРУКЦИИ>", "url": null},
     "examples": ["Как почистить станцию НОВАЯ МОДЕЛЬ?"]
   }
   ```

   `station_id: null` означает общий факт, независимо от модели. Именно так задан
   предоставленный ответ о первичных действиях при переполнении — он применим и
   при неизвестной модели. Это **не** инструкция по обслуживанию Твери.

3. Для исправления ответа существующей пары модель/тема измените её `answer`,
   а не создавайте дубликат. Для новой темы добавьте её в `intents`, выражения и
   примеры; пересмотрите запрещённые темы только при наличии утверждённых сведений.
4. Обновите `revision`, проверьте базу и тесты, затем перезапустите процесс:

   ```bash
   python -m service_bot validate-kb
   pytest
   python -m service_bot serve
   ```

После этого ИИ-модель сразу увидит новую запись: её описание и примеры входят в промпт,
а текст ответа по-прежнему берётся из JSON дословно. Достоверность содержания
подтверждает сервисный отдел; валидатор проверяет только структуру.

Другой путь к базе можно задать через `KNOWLEDGE_BASE_PATH`. База загружается при
старте и хранится в неизменяемой структуре; сообщения клиентов её не редактируют.

## Как исключены выдуманные ответы

```text
текст → правила (жёсткие запреты) → ИИ только выбирает запись → ответ из JSON дословно
                          ↓                                        ↓
        нет записи / неизвестная модель / тема вне базы → фиксированный отказ
```

- **У ИИ нет права писать текст.** Единственный конструктор фактического ответа —
  `AnswerEngine.answer_reply()`; он копирует `entry.answer` из базы. Промпт запрещает
  модели пересказывать ответ, а её вывод ограничен JSON-решением.
- **Ответ принимается только на существующую запись.** Несуществующий `entry_id`,
  неразобранный JSON, таймаут, 429/5xx — всё это переводит ответ на правила базы
  (`layer: rules_fallback`), а не в свободную генерацию.
- **Проверка модели станции и темы.** Выбор модели сверяется с распознанной моделью и
  темой (`_compatible`): нельзя выдать инструкцию КАН за КИТ и наоборот.
- **Проверка лексической близости.** Выбранная запись должна делить хотя бы одно
  значимое слово с вопросом (`_overlap`). Слабый ответ на посторонний вопрос
  («Кто написал Войну и мир?») отбрасывается.
- **Жёсткие запреты до ИИ.** Неизвестные модели («Тверь», «КАН Ультра 2», «КИТ-5»),
  темы вне базы (цена, ремонт, гарантия, фильтр, насос), несколько моделей или тем,
  отрицания — ИИ не спрашивают вовсе, клиент получает честный отказ.
- **Уточнение вместо догадки.** «Как самому обслужить станцию?» без модели приводит к
  вопросу о модели станции (текстом или кнопкой); после выбора КАН Ультра тот же вопрос
  возвращает видео, а выбор КИТ не создаёт отсутствующую инструкцию по очистке.
- **Резервный режим без ИИ.** Если все модели недоступны, бот продолжает работать на
  детерминированных правилах и никогда не «додумывает» ответ.

Модель станции запоминается на 15 минут отдельно для каждого пользователя/веб-сессии;
есть сброс и ограничение числа сессий. Ключи API не выводятся в статусы, ответы и логи,
вопросы клиентов не журналируются.

## Быстрый запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m service_bot validate-kb
python -m service_bot serve --host 0.0.0.0 --port 8000
```

Без токена и без ключей запускается веб-демо с детерминированными ответами. Чтобы
включить ИИ-слой локально, задайте `LLM_API_KEY` и при необходимости `LLM_MODEL`
(см. `.env.example`), либо запустите `python -m service_bot ai-check`, чтобы проверить
настройку. В Arena демо доступно в live preview; локально — `http://localhost:8000`.

### Подключение настоящего Telegram

1. Откройте https://t.me/BotFather, выполните `/newbot` и получите токен.
2. `cp .env.example .env` и заполните `TELEGRAM_BOT_TOKEN`. **Не присылайте токен в чат
   и не добавляйте его в Git.** `.env` исключён из Git и Docker-контекста.
3. Запустите `python -m service_bot serve` (веб-демо + Telegram) или
   `python -m service_bot telegram` (только бот). Не запускайте два polling-процесса
   с одним токеном.
4. Отправьте боту `/start` и напишите вопрос обычным текстом.

**Команды:** `/start` — начало диалога, `/help` — помощь, `/status` — режим работы
(какая ИИ-модель подключена, версия базы), `/reset` — сброс модели станции.
Кнопки остались только как подсказки в приветствии и при уточнении модели —
любой вопрос можно задать текстом.

## Хостинг на GitHub

- **`.github/workflows/telegram-host.yml` — постоянная работа (после мержа в `main`).**
  Каждые 6 часов запускается один polling-процесс на 5ч45м, следующий запуск
  поднимает бота сразу после предыдущего. ИИ-слой включён по умолчанию на бесплатном
  keyless-шлюзе `llm7`; провайдер меняется переменной репозитория `LLM_PROVIDER`,
  ключ (если нужен) хранится в секрете `LLM_API_KEY`.
- **`.github/workflows/telegram-demo.yml` — приёмочная живая сессия** на 5–348 минут
  по кнопке *Run workflow* (или автоматически при push в рабочую ветку). Внутри: тесты,
  проверка базы, `ai-check` и живое подключение Bot API.
- Оба workflow используют одну concurrency-группу, поэтому два polling-процесса
  никогда не пересекаются. Нужен только repository secret `TELEGRAM_BOT_TOKEN`.
- GitHub Actions — это не «вечный» сервер: расписание может задерживаться, а workflow
  отключается после 60 дней без активности репозитория. Для настоящего 24/7 есть
  Dockerfile и инструкции в `DEPLOYMENT.md`.

(имитация провайдера через `httpx.MockTransport`) и отрицательные сценарии:
`tests/test_ai.py`, `tests/test_llm.py`. Реальные сетевые вызовы в тестах запрещены:
`tests/conftest.py` удаляет ключи и токены из окружения. Текущий результат —
**279 тестов, покрытие 96%** (см. `VERIFICATION.md`).


## Структура

```text
knowledge/knowledge_base.json   факты, модели, темы и синонимы
service_bot/knowledge.py        строгая проверка базы
service_bot/matcher.py          распознавание моделей и тем, неизвестные слова
service_bot/engine.py           политика ответов, контекст, дословные ответы
service_bot/llm.py              транспорт ИИ: провайдеры, JSON-вердикты, предохранитель
service_bot/ai.py               промпт, дигест базы и проверки выбора модели
service_bot/telegram.py         long polling через официальный Bot API
service_bot/deployment.py       проверка API и плановые сессии
service_bot/web.py              веб-демо и JSON API
service_bot/static/             интерфейс демо
service_bot/__main__.py         команды serve/telegram/probe-telegram/ai-check/validate-kb
scripts/preview_llm_stub.py     офлайн-заглушка модели только для превью без сети
scripts/check_demo.py           desktop/mobile проверка в браузере
tests/                          правила, база, Telegram, веб-API, ИИ-слой
VERIFICATION.md                 фактические результаты проверки
DEPLOYMENT.md                   секреты, хостинг и ограничения GitHub Actions
```

Веб-API: `GET /health`, `GET /api/status` (включая состояние ИИ-слоя и цепочки
провайдеров), `GET /api/knowledge`, `POST /api/chat` (`text`, `session_id` в формате
UUID), `POST /api/reset` (`session_id`). Ответ `POST /api/chat` содержит `ai.layer`
(`llm`, `rules`, `rules_guard`, `rules_fallback`) и `ai.provider` — по ним видно, кто
принял решение.

Опционально предоставлен Dockerfile:

```bash
docker build -t tgbot-service .
docker run --rm --env-file .env -p 8000:8000 tgbot-service
```

Прототип намеренно не включает CRM, заявки, авторизацию веб-демо, долговременную
историю, общий поиск по документам или промышленный мониторинг.
