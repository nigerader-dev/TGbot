# Сервисный Telegram-бот: ответы только из базы знаний

Небольшой прототип на Python 3.11+. Telegram и интерактивное веб-демо используют
**один `AnswerEngine`**. Генеративной модели, внешнего поиска, платного ИИ API и
автоматического дополнения ответов нет.

## Что реализовано

| Вопрос | Ответ |
| --- | --- |
| Как почистить / обслужить КАН Ультра? | Видео: https://youtu.be/WW1Hqh3_WNk |
| Как часто обслуживать КИТ? | Рекомендуем проводить обслуживание один раз в год. |
| Станция переполнена, что делать? | Точный предоставленный ответ о проверке электрического блока, обесточивании при затоплении и обращении в сервис. |
| Как почистить станцию Тверь? | Нет информации в базе; обращение в сервисный отдел. |

Фактический ответ копируется из поля `answer` целиком, без пересказа и дополнений.
Бот не переносит периодичность КИТ на КАН и не выдаёт видео КАН за инструкцию для
другой станции. Телефон и адрес сервисного отдела не предоставлены и не выдумываются.

**Проверенный Telegram-бот:** https://t.me/TestBotKovaleuski_bot — отправьте `/start`.

Подключение к настоящему Bot API проверено через GitHub Actions. Сейчас предусмотрена
**ограниченная 15-минутная приёмочная сессия**, не постоянный хостинг. Проверенный
запуск: https://github.com/nigerader-dev/TGbot/actions/runs/37057492836. Плановое окончание этой сессии —
**02.10.2026 23:14 (Минск / Москва)**. После этого бот останавливается;
повторный ручной тест запускается через Re-run all jobs. Для постоянной работы нужен
отдельный сервер. Настройка: `DEPLOYMENT.md`; результаты: `VERIFICATION.md`.

Веб-демо имеет собственный локальный статус процесса Telegram. Он не отслеживает
удалённый процесс GitHub Actions: отсутствие локального токена не означает, что
отдельная приёмочная сессия в Actions не работает.

## Быстрый запуск

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m service_bot validate-kb
python -m service_bot serve --host 0.0.0.0 --port 8000
```

Без токена запускается веб-демо. В Arena оно доступно в live preview
**«Демо сервисного бота»**. При локальном запуске откройте `http://localhost:8000`.
Интерфейс включает диалог, четыре проверочных вопроса, полную базу знаний и
**реальный**, а не декоративный, статус Telegram-подключения.

### Подключение настоящего Telegram

1. Откройте https://t.me/BotFather, выполните `/newbot` и получите токен.
2. Создайте локальный конфигурационный файл:

   ```bash
   cp .env.example .env
   ```

3. В `.env` заполните `TELEGRAM_BOT_TOKEN` полученным токеном. **Не присылайте токен
   в чат и не добавляйте его в Git.** `.env` и другие файлы `.env.*` исключены из Git
   и Docker-контекста; публикуется только пустой `.env.example`.
4. Остановите предыдущий процесс и запустите:

   ```bash
   python -m service_bot serve
   ```

   Этот режим запускает веб-демо и Telegram long polling вместе.
   Если нужен только Telegram без веб-сервера:

   ```bash
   python -m service_bot telegram
   ```

5. Откройте созданного бота и отправьте `/start`. Проверьте четыре вопроса выше.

Токен читается из окружения или `.env`; уже заданные переменные окружения имеют
приоритет. Не запускайте два polling-процесса для одного токена.

**Команды:** `/start` — начало диалога и кнопки примеров; `/help` — помощь;
`/reset` — сброс выбранной модели. Прототип обрабатывает личные чаты, принимает
текст и поддерживает inline-кнопки. В группах сообщения игнорируются.

При активном webhook бот не удаляет чужие настройки автоматически: подключение
останавливается с понятным сообщением. Ошибки авторизации и конфликт второго
polling-процесса отображаются в статусе. При временных сетевых ошибках и HTTP 429
выполняются повторные попытки. Блокировка бота одним пользователем не останавливает
обслуживание остальных. Неудачная отправка повторяется с тем же текстом ответа.

## Где база знаний и как её менять

**`knowledge/knowledge_base.json` — единственный источник фактических ответов.**

- `stations`: идентификаторы моделей, названия и допустимые варианты написания.
  «КАН» — явно заданный синоним «КАН Ультра» в этом прототипе, не правило для всех КАН.
- `intents`: темы и словари формулировок: обслуживание, периодичность, переполнение.
- `entries`: модель + тема + утверждённый ответ + источник + проверочные примеры.
- `context_word_patterns`: допустимые служебные слова и формы русского языка.
- `unsupported_topic_patterns`: темы, которых нет в текущей базе, например ремонт,
  химические средства, цены и монтаж.

### Пример добавления сведений о новой модели

Сначала сервисный отдел должен предоставить точный текст. **Не добавляйте сведения
из предположений или общих знаний ИИ.** Существующая база специально не содержит
инструкции для Твери.

1. Добавьте в `stations` модель (название должно входить в `aliases`):

   ```json
   {
     "id": "new_station",
     "name": "НОВАЯ МОДЕЛЬ",
     "aliases": ["НОВАЯ МОДЕЛЬ"]
   }
   ```

2. Добавьте в `entries` запись, подставив настоящий утверждённый текст и источник:

   ```json
   {
     "id": "new_station_maintenance",
     "station_id": "new_station",
     "intent_id": "maintenance",
     "title": "Обслуживание НОВОЙ МОДЕЛИ",
     "answer": "<ТОЧНЫЙ ТЕКСТ, УТВЕРЖДЁННЫЙ СЕРВИСНЫМ ОТДЕЛОМ>",
     "source": {
       "label": "<НАЗВАНИЕ ПРЕДОСТАВЛЕННОЙ ИНСТРУКЦИИ>",
       "url": null
     },
     "examples": ["Как почистить станцию НОВАЯ МОДЕЛЬ?"]
   }
   ```

   `station_id: null` означает общий факт, независимо от модели. Именно так задан
   предоставленный ответ о первичных действиях при переполнении — он применим и
   при неизвестной модели. Это **не** инструкция по обслуживанию Твери.

3. Для исправления ответа существующей пары модель/тема измените её `answer`,
   а не создавайте дубликат. Для новой темы добавьте её `intents`, выражения и
   примеры; пересмотрите запрещённые темы только при наличии утверждённых сведений.
4. Обновите `revision`, проверьте базу и тесты, затем перезапустите процесс:

   ```bash
   python -m service_bot validate-kb
   pytest
   python -m service_bot serve
   ```

   Тест `test_all_kb_examples_return_their_own_entry` проверяет, что все примеры из
   базы возвращают именно свои записи. Валидатор проверяет структуру, ссылки,
   уникальность пар модель/тема, синонимы и регулярные выражения. Достоверность
   содержания должен подтверждать сервисный отдел, не структурный валидатор.

При добавлении ранее неизвестных сведений обновите связанные отрицательные
приёмочные проверки: например, если сервис действительно предоставит инструкцию
для Твери, этот вопрос больше не должен проверяться как «нет информации».

Другой путь к базе можно задать через `KNOWLEDGE_BASE_PATH`. База загружается при
старте и хранится в неизменяемой структуре; сообщения клиентов её не редактируют.
Некорректная или отсутствующая база блокирует запуск, а не включает общие знания.

## Как исключены выдуманные ответы

```text
Текст → нормализация → модель и тема → проверка области действия
                              ↓
        точная запись есть → answer из JSON дословно
        нет записи / неизвестные термины → фиксированный отказ + сервис
        модель не указана / несколько моделей → уточнение, без угадывания
```

- **Нет свободной генерации:** единственный конструктор фактического ответа
  `AnswerEngine._answer()` получает существующую `Entry` и копирует `entry.answer`.
- **Не ищем «самый близкий» ответ любой ценой:** должны совпасть и модель, и тема.
  Дополнительные неизвестные модели/модификации и непонятные слова приводят к отказу.
- **Контекст не заменяет явно указанную неизвестную модель:** «Тверь» после «КАН»
  сбрасывает прежнюю модель, а не наследует её инструкцию.
- **Уточнение вместо догадки:** «Как самому обслужить станцию?» без модели вызывает
  выбор модели. После выбора КАН Ультра тот же вопрос возвращает видео. Выбор КИТ
  не создаёт отсутствующую инструкцию по очистке.
- **Синонимы, формы слов и порядок слов:** «почистить», «промыть», «обслужить»,
  «видеоинструкция», «периодичность», «интервал» и другие проверенные формулировки
  относятся к темам. Распознавание ограничено словарями маленькой базы — это не
  универсальное понимание любых русских фраз. Неуверенность означает отказ.
- Веб и Telegram используют одну политику. Веб показывает источник ответа;
  отказу источник не приписывается. Telegram отправляет plain text, веб использует
  `textContent`, а не интерпретацию сообщений как HTML.

Модель запоминается на 15 минут, отдельно для каждого пользователя/веб-сессии.
Есть сброс и ограничение числа сессий. На сервере не сохраняется журнал диалогов;
в памяти находятся контекст модели и незавершённый ответ для повторной отправки.
Токен не выводится в статус, ответы и логи приложения.

## Проверки

```bash
pip install -r requirements-dev.txt
python -m service_bot validate-kb
ruff check .
ruff format --check .
pytest --cov=service_bot --cov-report=term-missing --cov-fail-under=90
```

Результат проверки: **193 теста прошли, покрытие ядра и адаптеров — 98%**.
В том числе 400 случайно сформированных запросов с неизвестными названиями в
отдельном тесте. Telegram Bot API в автоматических тестах имитируется;
реальных токенов и внешних сетевых запросов тестам не требуется.
GitHub Actions настроен на те же проверки. Это конфигурация CI, не утверждение
о выполненном удалённом запуске.

Дополнительно проверен настоящий Chromium: четыре сценария, уточнение, сброс,
база, статус Telegram, сетевой сбой и мобильный экран. Повторить при работающем демо:

```bash
pip install -r requirements-browser.txt
python -m playwright install chromium
python scripts/check_demo.py
```

Для установленного отдельно Chromium можно задать `BROWSER_EXECUTABLE`.
Скрипт ожидает режим без Telegram-токена и принимает `--url` для другого адреса.

## Структура

```text
knowledge/knowledge_base.json   факты, модели, темы и синонимы
service_bot/knowledge.py        строгая проверка базы
service_bot/matcher.py          ограниченное распознавание вопросов
service_bot/engine.py           политика ответов и контекст
service_bot/telegram.py         long polling через официальный Bot API
service_bot/deployment.py       проверка API и ограниченная живая CI-сессия
service_bot/web.py              веб-демо и JSON API
service_bot/static/             интерфейс демо
service_bot/__main__.py         команды запуска
scripts/check_demo.py           desktop/mobile проверка в браузере
tests/                         проверки правил, базы, Telegram и веб-API
VERIFICATION.md                фактические результаты проверки
DEPLOYMENT.md                  безопасный запуск и ограничения GitHub Actions
```

Веб-API: `GET /health`, `GET /api/status`, `GET /api/knowledge`,
`POST /api/chat` (`text`, `session_id` в формате UUID), `POST /api/reset` (`session_id`).

Опционально предоставлен Dockerfile (не запускался в этой проверочной среде):

```bash
docker build -t tgbot-service .
docker run --rm --env-file .env -p 8000:8000 tgbot-service
```

Прототип намеренно не включает CRM, заявки, авторизацию веб-демо, долговременную
историю, общий поиск по документам или промышленный мониторинг. Для размещения
публичного веб-демо вне тестовой среды потребуются дополнительные лимиты и защита.
